PALS · Module GLY (GuidePal)

GLY Pipeline Architecture

GLY is the front desk of PALS. It hears every user message and either answers PayPal questions itself or hands the job to ARB or PULSE. This page lays out every pipeline inside GLY: what starts it, each step in order, which shared module each step uses, and what it must never do.

P1

Message In

GLY only

The door. Every message the user types comes through here before anything else happens.

Starts when
User sends a chat message
Ends with
An InboundMessage handed to P2
Speed target
Under 50 ms
  1. Receive on the socket chat/socket.ts

    WebSocket server gets the raw text, user id and session id.

  2. Validate the shape shared/types

    Zod checks the message. Empty, too long (over ~4,000 chars) or malformed messages are rejected with a friendly error.

  3. Give it an ID shared/logging

    Create a correlationId. Every log line and every envelope from here on carries it, so one message can be traced across all PALs.

  4. Load session context chat/session.ts

    Fetch the last ~10 turns and the list of tasks still running for this user. The router needs these to understand "the cheaper one" or "is it done yet?".

  5. Hand off to Intent Routing

    Pass the InboundMessage with its context to P2.

P2

Intent Routing

GLY only

The brain. Works out what the user wants, then picks the next pipeline. The LLM only labels the message. Plain code makes the routing decision.

Starts when
P1 hands over a message
Ends with
An IntentResult and a chosen pipeline
Model
Claude Haiku 5.5 (fast, cheap)
Speed target
Under 800 ms
  1. Build the prompt intent/prompt.ts

    Message, short history, open tasks and the list of allowed intents with one example each.

  2. Ask the LLM for structured output shared/llm

    Tool / function calling forces the reply into JSON: intent, confidence, extracted entities (product, budget, order id…).

  3. Parse with Zod intent/schema.ts

    If the JSON does not match the schema, retry once. If it still fails, treat it as unclear.

  4. Confidence gate

    Confidence below 0.6 or a missing required entity (for example, no product named) gets a clarifying question, not a guess.

  5. Route intent/router.ts

    A plain lookup table (below) picks P4, P5 or a direct reply.

IntentExample messageGoes to
paypal_guidance"How long do I have to open a dispute?"P4 RAG Answer
shopping_research"Find me noise-cancelling headphones under $200"P5 → ARB research.start

P3

Knowledge Ingest

Batch · offline

The library builder. Runs as a script, not during chat. It turns PayPal's docs into searchable pieces.

Starts when
You run npm run ingest, or docs change
Ends with
Tagged chunks stored in pgvector
Source
docs/knowledge/paypal/*.md
  1. Collect official docs docs/knowledge/paypal/

    Only official PayPal consumer and developer pages, saved as Markdown with the source URL and date at the top of each file.

  2. Clean rag/ingest/clean.ts

    Strip navigation, footers and cookie text. Keep headings, lists and tables.

  3. Chunk by heading rag/ingest/chunk.ts

    Split on H2/H3 into ~500–800 token pieces with ~100 tokens of overlap. Never cut a table or numbered procedure in half.

  4. Tag metadata

    Each chunk gets sourceUrl, section, audience (consumer / developer), region, topic (fees, disputes, KYC, API…) and docDate.

  5. Skip unchanged chunks

    Hash each chunk's text. If the hash already exists in the store, skip it, which keeps re-runs cheap.

  6. Embed and upsert shared/db/vector

    Create embeddings and write them to pgvector with a corpusVersion. Delete chunks whose source page was removed.

P4

RAG Answer

GLY only

The librarian. It answers PayPal questions using only what the docs say, and it says so when the docs don't cover something.

Starts when
P2 routes paypal_guidance
Ends with
A streamed answer with source links
Speed target
First words in under 1.5 s
  1. Rewrite the question

    Turn "what about for sellers?" into a standalone question using the chat history.

  2. Search shared/db/vector

    Embed the question and fetch the top 8 chunks, filtered by metadata where the intent gave hints (audience, region, topic).

  3. Confidence check

    If the best match scores below the threshold, reply: "I couldn't find that in PayPal's official docs", with a link to PayPal Help. Never guess a policy.

  4. Generate a grounded answer shared/llm

    The prompt says to use only these chunks and cite each fact as [1], [2]. A stronger model works best here.

  5. Stream and cite chat/socket.ts

    Stream tokens to the user, then attach the source links for each citation.

P5

Delegation

ARBPULSE

The dispatcher. Packs the job, sends it through calls/, and tells the user straight away. It never waits for the result.

Starts when
P2 routes a shopping or transaction intent, or P7 sends an approval
Ends with
Task saved as pending, plus an instant reply
Speed target
Acknowledgement in under 1 s
  1. Build the payload delegation/payloads.ts

    Map entities into the right typed payload: ARBResearchPayload, PurchaseProposal, TransactionQueryRequest or PulsePaymentRequest.

  2. Wrap in an envelope delegation/envelope.ts

    PalCallEnvelope with taskId, correlationId, sessionId, action, payload and an idempotencyKey so a retry can't start the job twice.

  3. Send via calls/ calls/

    calls/ replies "accepted" right away. GLY does not await the work itself. It never talks to ARB or PULSE directly.

  4. Record the task

    Save {taskId, action, status: "pending", createdAt} on the session so the user can ask "is it done?".

  5. Reply now

    "Looking for headphones under $200. I'll show you when it's ready. Ask me anything meanwhile."

  6. If calls/ refuses

    Retry once with the same idempotency key. If it fails again, tell the user plainly and log the error. Don't loop.

P6

Results Back

GLY only

The mail room. Listens for finished work and puts it in front of the user as a clean card.

Starts when
An event arrives on shared/tasks
Listens for
task.progress, task.completed, task.failed, proposal.ready
Ends with
A card in the chat, task status updated
  1. Subscribe events/listener.ts

    One long-running subscriber for GLY's events, started when the server boots.

  2. Match to a session

    Look up taskId. Ignore duplicates (same event id twice) and events for unknown tasks.

  3. Pick a card events/cards.ts

    ProductResultsCard, ProposalCard (goes to P7), TransactionSummaryCard, PaymentReceiptCard or ErrorCard.

  4. Deliver

    If the user is online, push to the socket. If not, save it to an inbox and show it on their next connect.

  5. Stale tasks

    A pending task with no event after ~5 minutes gets a gentle "still working on it" note. Never a silent failure.

P7

Approval

Ends at PULSE

The only road to a payment. GLY shows the card and passes on the user's yes. PULSE does the actual paying.

Starts when
ARB emits proposal.ready
Ends with
payment.execute sent to PULSE, or the proposal closed
Key rule
Typed chat text alone never triggers payment
  1. Proposal arrives

    Via P6: item, merchant, final price, coupon applied, proposalId and expiry time.

  2. Show the approval card

    Clear total in the user's currency, what it's for, and two buttons: Approve and Reject.

  3. Check before sending

    Proposal not expired, belongs to this user, not already approved. If it fails any check, explain why and offer to refresh the deal via ARB.

  4. Send payment request calls/

    Go through P5 with action='payment.execute' and PulsePaymentRequest {proposalId, userId}. Use the proposalId as the idempotency key so a double tap pays once.

  5. Acknowledge

    "Sent to PULSE for payment." The receipt comes back through P6.

Shared data shapes

These live in shared/types and must match API_CONTRACTS.md. Field names here are a proposal to agree with the ARB and PULSE owners.

// What P1 produces
type InboundMessage = {
  messageId: string; sessionId: string; userId: string;
  text: string; receivedAt: string; correlationId: string;
  history: ChatTurn[]; openTasks: TaskRef[];
};

// What P2 produces (validated by Zod)
type IntentResult = {
  intent: "paypal_guidance" | "shopping_research" | "purchase_prep"
        | "transaction_query" | "payment_request" | "task_status"
        | "smalltalk" | "unclear";
  confidence: number;            // 0–1, below 0.6 asks a question
  entities: { product?: string; budget?: number; currency?: string;
              orderId?: string; dateRange?: { from: string; to: string } };
};

// What P5 sends through calls/
type PalCallEnvelope<T> = {
  taskId: string; correlationId: string; sessionId: string;
  from: "GLY"; to: "ARB" | "PULSE";
  action: "research.start" | "purchase_prep.start"
        | "payment.execute" | "transaction.query";
  idempotencyKey: string; payload: T; sentAt: string;
};

// What P6 receives from shared/tasks
type TaskEvent = {
  eventId: string; taskId: string;
  type: "task.progress" | "task.completed" | "task.failed" | "proposal.ready";
  data: unknown; at: string;
};

Testing and rules that apply everywhere

Tests that prove the contract

  • Non-blocking test: fake ARB takes 30 s. GLY must still ack in under 1 s and answer a second message meanwhile.
  • Intent eval: labelled set, run on every change. Watch for payment phrases being misread.
  • RAG golden set: real questions with known answers and sources.
  • No-hallucination test: made-up policy questions must get "not found".
  • Boundary test: GLY code has no imports of Playwright, PayPal SDKs or ARB/PULSE modules. A lint rule can enforce this.

Rules for every pipeline

  • Every log and envelope carries the correlationId.
  • Nothing in the chat path awaits ARB or PULSE work.
  • All cross-PAL traffic goes through calls/.
  • No secrets in GLY: no PayPal keys, no card data.
  • Every failure tells the user something. Nothing fails silently.
  • Retries reuse the same idempotency key.

Questions to settle with the team

  • Orchestrator vs calls/: the README says tasks go to "the Orchestrator", but RESPONSIBILITIES says everything goes through calls/. This plan assumes calls/ is the way into the Orchestrator. Confirm who owns it.
  • Event names: agree the exact TaskEvent types with ARB and PULSE, especially proposal.ready.
  • Model choice: ADR-GLY-001 names Claude 3.5 Haiku, which is outdated. Update it to Claude Haiku 5.5 for routing.
  • Refunds: should a refund also go through an approval card? This plan says yes, to keep one road to money movement.
